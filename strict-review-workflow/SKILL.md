# 强审开发工作流

把本 skill 当作协作纪律，而不是不可绕过的流程控制器。只依赖当前 Agent 运行时已有的文件、验证和子 Agent 能力；不要为执行本流程引入脚本、数据库、viewer、状态解析器或任务 checklist 文件。

## 明确边界

- 保证角色分离、证据驱动验证和独立审查循环。
- 不声称保证持久化、原子状态转换、可信身份、并发锁或对恶意 Agent 的强制约束。
- 只在用户要求实施或修改时写文件。对只读咨询、诊断或审查任务，不修改项目 `AGENTS.md` 或源码。
- 用户只要求只读审查时，只执行任务对齐和独立审查并报告发现；跳过项目约束写入、实现、返工和开发完成门禁，除非用户随后明确要求修复。
- 把用户原始请求作为完成边界。不得用自行拆出的阶段、批次或里程碑缩小范围。
- 把“通过”定义为验收标准满足且没有未解决的阻塞项，而不是 Reviewer 再也提不出任何改进意见。
- 无人值守表示启动契约冻结后不要求人工参与执行和返工循环；它不意味着遇到超出授权或无法消除的高风险不确定性时必须猜测并完成。

## 写入项目约束

在启动对齐期间找到仓库根目录并读取适用的 `AGENTS.md`。由协调者判断是否需要补充项目约束；启动门禁通过后，把该写入明确纳入实现 Agent 的任务范围并要求实现者优先完成，协调者不要亲自修改。让项目级指令持久记录本工作流，避免后续会话丢失关键约束。对 `AGENTS.md` 的改动必须进入最终 diff、验证和独立审查。

按以下优先级处理：

1. 默认在根级 `AGENTS.md` 中嵌入一段简短、自包含的“强审开发”规则。
2. 仅当已确认目标环境能够按名称发现本 skill 时，才可改为引用 `$strict-review-workflow`。
3. 项目需要脱离当前机器、skill 安装目录或特定 Agent 运行时独立工作时，必须嵌入规则，不得只引用 skill。
4. 已有等价规则时不要重复添加；已有 `AGENTS.md` 时保留其有效约定，只做必要补充。
5. 只有子目录确有不同风险或验证要求时，才在最近的嵌套 `AGENTS.md` 中补充差异。

嵌入内容至少表达：

- 高风险任务或明确要求强审开发时，分离协调者、实现者和独立审查者。
- 实现者先完成改动和新鲜验证，未参与实现的审查者再对照请求、diff 和测试做只读审查。
- 审查发现交回原实现者修复，并重复独立审查，直到没有阻塞问题。
- 无法提供真正独立审查时必须明确报告，不得把自审描述成独立审查。
- 实现前冻结范围、验收标准、自治边界、阻塞定义、验证方式和停止条件；只有满足启动门禁才开始写入。
- 由协调者裁决审查意见；只有证据充分的阻塞项触发返工。预算内消除全部阻塞项才可完成；预算耗尽仍有有效阻塞项时必须报告 `blocked`，不得无限循环或强行通过。
- 无人值守时，超出自治边界、存在无法消除的高风险不确定性或缺少必要能力时必须报告 `blocked`，不得猜测、放宽边界或自行定义更宽松的停止条件。

不要把会话状态、人员名称、临时任务拆分或本机绝对路径写入 `AGENTS.md`。

## 建立任务台账

在对话中维护简短台账，不创建或解析状态文件：

```text
任务：
目标：
范围：
明确不做：
验收标准：
风险：
必须保持的不变量：
自治边界：
阻塞定义：
验证方式：
返工预算：
停止条件：
实现者：
审查者：
验证证据：
审查状态：
阻塞项：
```

把台账作为协调提示，不把自然语言回复当作机器可验证状态。由协调者根据实际证据作出派工、返工和完成判断。

## 启动门禁

在任何实现写入前，由协调者形成并冻结执行契约。契约至少明确：

- 用户目标、范围、明确不做的事项和外部可观察的验收标准。
- 必须保持的兼容性、公共契约、安全边界和项目不变量。
- Agent 可以自主决定的事项、不得自行改变的事项以及必须停止的条件。
- 验证入口、阻塞项定义、审查范围、返工预算和完成条件。

按风险决定对齐深度：

- 低风险局部任务：优先从代码、测试和项目指令推断可逆细节，不进行形式化盘问。
- 标准任务：只对会实质影响范围、接口、安全、数据或用户行为的歧义提问；每次只问一个问题，并给出推荐默认项。
- 高风险或无人值守任务：沿决策依赖逐项消除关键歧义。能从仓库确认的事实自行调查，不把可侦察问题交给用户。
- 高风险无人值守任务：冻结前委派一个未参与制定契约的 Agent 做只读计划审查，检查范围遗漏、不可验证的验收标准、未定义自治边界和危险假设；协调者核实并处理有效发现，计划审查者不得扩大用户范围。

只有同时满足以下条件才能标记为 `ready` 并分配实现：

1. 范围和明确不做的事项有边界。
2. 验收标准能够通过测试、运行结果、可观察行为或 diff 判断。
3. 重要歧义已经解决，或明确委托协调者在自治边界内裁决。
4. 验证方法、阻塞标准、返工预算和停止条件已经确定。
5. 高风险变更的兼容性、安全、数据与回滚约束已经明确。

任何一项不满足时继续对齐或报告 `needs-clarification`，不得开始实现。

## 无人值守裁决

用户要求启动后不再人在环中时，在执行契约中明确自治权限。默认允许 Agent 决定符合现有模式的内部命名、局部结构、实现细节和必要测试；默认禁止自行扩大产品范围、改变公共 API 或持久化格式、放宽安全权限、接受不可逆数据风险或改变用户明确要求。

启动后遇到分歧时，由协调者按以下顺序裁决：

1. 可复现测试、静态检查和事实证据优先于推测。
2. 用户请求、冻结的验收标准和项目指令优先。
3. 兼容现有行为与不变量优先。
4. 多个方案同样有效时，选择满足要求的最小改动和现有项目模式。
5. 无充分证据的不确定意见视为问题或非阻塞建议，不得触发返工。
6. 超出自治边界或存在无法消除的安全、数据、权限和不可逆风险时，停止并报告 `blocked`，不得猜测。

不要在启动后为可逆的局部实现选择重新询问用户。只有执行契约明确允许中途澄清时才提问；否则在自治边界内裁决或按停止条件结束。

## 执行流程

### 1. 对齐任务

- 读取最相关的代码、项目指令和测试入口。
- 按启动门禁明确并冻结执行契约；未达到 `ready` 不得进入分配实现。
- 将任务分为低、中或高风险。安全、权限、秘密、不可逆数据、迁移、公共契约、关键架构、复杂并发或较大跨模块影响视为高风险。

### 2. 分配实现

- 由协调者定义任务边界、文件范围、验收标准和验证要求。
- 把实现交给一个实现 Agent。任务可独立且写入范围不重叠时才并行分配多个实现 Agent。
- 要求实现者只返回改动摘要、实际运行的验证、关键结果和剩余风险。
- 实现失败或测试失败时，先保留根因和证据，不得把部分成功写成完成。

### 3. 检查实现证据

- 检查实际 diff，确认改动可追溯到请求且没有无关重构。
- 要求新鲜、最小且直接相关的验证。命令名称、覆盖范围和关键结果必须可辨认。
- 不接受“应该通过”“看起来正常”或未运行的测试作为通过证据。
- 未满足验收标准时，交回原实现者继续处理，不进入审查通过状态。

### 4. 独立审查

- 委派一个未参与实现的 Agent 做只读审查。
- 提供用户请求、完整冻结执行契约、适用项目指令、最终 diff 和验证证据，使 Reviewer 能检查范围、明确不做、不变量、自治边界、阻塞定义和停止条件；不要泄露希望审查者得出的结论。
- 要求审查者把结果分为 `blocking`、`non-blocking` 和 `residual-risk`；没有未解决 `blocking` 时结论必须为 `PASS`，即使仍有建议。
- `blocking` 只允许用于违反冻结验收标准、可复现错误或回归、安全与数据风险、公共契约破坏，或改动行为缺少项目明确要求的必要测试。
- 每个 `blocking` 必须给出违反的标准、文件与行号、受影响行为、复现步骤或验证证据，以及为何必须在本次范围解决。证据不完整但只是改进建议时归为 `non-blocking`；可能存在实质风险但当前无法验证时归为 `residual-risk`。
- Reviewer 的 `PASS` 只是“未确认阻塞项”的审查结论，不等于协调者可以宣布完成。协调者必须逐项裁决 `residual-risk`：触及冻结停止条件、超出自治边界或构成未消除的高风险不确定性时必须转为 `blocked`；其余风险才可在最终回复中披露并与 `complete` 共存。
- 没有问题时，也要求明确说明审查范围、检查过的验证和剩余风险。
- 审查者不得顺手修改文件；角色一旦参与实现，就不能继续充当本轮独立审查者。

### 5. 返工与复审

- 由协调者先按冻结契约和证据裁决审查意见，只把有效 `blocking` 交回原实现者修复，并要求重新运行相关验证。
- 修复后再次把完整最终 diff 和新鲜验证交给独立审查者，不得只审最后一个补丁片段。
- 第一轮审查覆盖完整 diff；复审聚焦既有阻塞项、修复引入的回归、修复涉及的代码，以及新发现的高严重度正确性、安全或契约问题。不得把历史问题、请求外增强或新偏好升级为阻塞项。
- 优先保持同一位独立审查者以维持标准一致。只有其不可用、独立性失效或执行契约要求一次性高风险复核时才更换；不要每轮换新 Reviewer 累积随机意见。
- 每完成一次实现者修复并复审计为一轮。低、中风险默认最多自动返工两轮；高风险在执行契约中设定预算。预算耗尽后禁止再派发自动返工；若协调者核实仍有有效 `blocking`，唯一终态为 `blocked`。不得继续循环、忽略问题或降低标准强行 `PASS`。
- 审查意见不清楚或技术上可疑时，先用代码和测试核实；不得盲从，也不得无证据忽略。

### 6. 最终门禁

协调者在宣布完成前必须独立检查：

- 用户原始范围内的事项均已完成。
- 最终 diff 与项目指令一致，没有未解释的额外改动。
- 关键验证基于最终工作区重新运行并通过。
- 最后一轮独立审查没有阻塞发现。
- 最终回复区分已验证事实、未运行检查和剩余风险。

全部满足时终态才是 `complete`。存在超出自治边界的决策、无法消除的高风险不确定性、能力缺失，或返工预算耗尽后仍有有效阻塞项时，终态是 `blocked`，并报告阻塞证据、已完成部分和未满足条件。`blocked` 不是完成，不得套用完成措辞。

## 能力降级

- 运行时没有子 Agent 能力时，高风险任务或用户明确要求真正独立审查的任务必须报告阻塞。
- 对低、中风险任务，只有用户接受降级时才可由同一 Agent 实现并自审；最终回复必须明确标注“自审”，不得称为独立审查。
- 子 Agent 不可用、超时或上下文不足时，先尝试重新委派或缩小独立任务边界；不要伪造角色、审查结论或验证结果。

## 停止条件

满足验收标准、最终验证通过且独立审查无阻塞问题后停止。不要为了让流程显得更严格而增加无关文档、抽象、测试基础设施或额外轮次。
